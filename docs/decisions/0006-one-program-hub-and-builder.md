# 0006. The Hub and the Builder in one program, with checked boundaries

## Context

The founder asked whether the Hub and the Builder should be two programs; two studies compared both forms.

## Decision

One program at launch, two modules. The Builder reaches the Hub only through named ports; CI refuses a Builder file that reaches the Hub's database without a port, and new memory state seen by both sides. Basis: Purpose: fewer pieces for one person to publish and restore; creating a run and delivering an app stay one transaction; the way to split stays open. The bridge-cost reason leans on implemented so and is accepted because it would be new code even in an empty repository.

## Criterion

None written before. Brought from earlier work.

## Result

Two turns of two companies at once peaked at 23.3% of server memory. 148 of 150 cross attempts were refused by admission, 2 earlier by format. One process only was ever run.

## Consequences

A Builder defect can reach the Hub.

## Reopens when

Updates interrupt people; a Builder defect takes the Hub down; server memory passes 70%. Split, if needed, is the same image started in Builder mode.
